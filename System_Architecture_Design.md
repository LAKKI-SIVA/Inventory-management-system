# System Architecture Design Document
**Project:** Enterprise Inventory Management System
**Architecture Pattern:** Modular Monolith / 3-Tier Architecture

This document provides a high-level overview of the System Architecture, detailing how data flows from the end-user down to the database and how the various components interact.

## 2. Component Breakdown

### A. The Client Tier (Frontend)
The system is designed to handle multiple types of clients:
1. **Web Users:** Access the system via standard web browsers. They receive Server-Side Rendered HTML and CSS generated by Django Templates.
2. **API Consumers:** Mobile applications or modern JavaScript frontends (like React/Vue) can communicate with the system using the RESTful JSON API.

### B. The Gateway Tier (Reverse Proxy)
**Technology:** Nginx
Nginx sits at the edge of our network. It is responsible for:
- **Routing:** Forwarding API and Application requests to the Django backend.
- **Static File Serving:** Bypassing Django entirely to serve CSS, JavaScript, and user-uploaded media files (product images) directly from the filesystem at high speeds.
- **Security:** Hiding the internal application server from direct internet access.

### C. The Application Tier (Backend Logic)
**Technology:** Python, Django, Gunicorn
This is the "Brain" of the operation. It is built as a **Modular Monolith**, meaning all components live in one codebase but are strictly separated into modules (Accounts, Products, Inventory, Orders).
- **Authentication (JWT/Session):** Validates the user's identity and checks their Role-Based Access Control (Admin, Manager, Customer).
- **Service Layer:** Business logic (like deducting inventory or calculating order totals) is decoupled from the web views. It is handled by dedicated Python service functions.
- **Django ORM:** Translates Python object manipulations into safe, secure SQL queries to prevent SQL Injection attacks.

### D. The Data Tier (Persistence)
**Technology:** PostgreSQL & Docker Volumes
- **PostgreSQL 15:** Acts as the single source of truth for all transactional data. It is highly normalized and enforces data integrity using Foreign Keys and atomic transactions.
- **Docker Volumes:** Because Docker containers are stateless, Docker Volumes are mounted to the host machine to ensure the PostgreSQL data and user-uploaded media files are permanently persisted, even if the containers crash or restart.

## 3. Data Flow Example: Placing an Order

To understand the architecture, here is the exact path data takes when a customer places an order:

1. **Request:** The Client sends a `POST /orders/api/` request containing a JWT token and the cart data.
2. **Routing:** Nginx receives the HTTP request and proxies it to Gunicorn.
3. **Authentication:** Django intercepts the request, validates the JWT token, and confirms the user has the `CUSTOMER` role.
4. **Business Logic (Service Layer):** The Order Service initiates an **atomic database transaction**. 
   - It queries the ORM to check current inventory levels.
   - It deducts the purchased quantity from the `Inventory` table.
   - It writes a new `Order` and `OrderItem` record.
5. **Persistence:** The ORM safely commits the SQL transaction to PostgreSQL.
6. **Response:** Django generates a JSON success response, which Nginx forwards back to the client.
